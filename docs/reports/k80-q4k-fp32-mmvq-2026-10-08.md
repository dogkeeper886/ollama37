# q4_K mat-vec with FP32 decode on the K80 (#563)

| | |
|---|---|
| Build | branch `study-563-k80-fp32-dequant` on `b634eb63`, built with `build-local.sh`, version 2.3.3-563 |
| Baseline | `dist/bin/ollama` 2.3.3 (`b634eb63` less CI-only commits), same host, same day |
| Host | 4 × Tesla K80 dies (sm_37), CUDA 11.4, driver 470.256.02, ECC on |
| Measured | 2026-10-08, one die per small model; die clocks 562–666 MHz under load (power cap, auto boost) |

Batch-1 decode spends most of its time in the quantized mat-vec. On the K80, ggml's
`mul_mat_vec_q` reaches about a third of what the die can read, because Kepler has no dp4a and
converts int to float at 1/6 of its FP32 FMA rate. `mmvq_k80_q4_K` decodes each 4-bit value to
FP32 with an OR and an FADD (the value sits in the mantissa of 2^23), and each warp shares the
input vector across four rows. It handles q4_K at batch 1 on Kepler; every other case keeps
ggml's path.

## Kernel, one die

`nvprof --print-gpu-summary`, average kernel time over 100–200 launches, random q4_K weights,
the lab program in [`bench.cu`](https://github.com/dogkeeper886/ollama37/blob/d8ac96ec/docs/reports/k80-q4k-fp32-mmvq/bench.cu) (removed after #565). Each cell is
the range over 2–3 runs; the clock drift below moves single runs by up to 20 %. Baseline runs
used the 2.3.3 `libggml-cuda.so`, the #563 runs the rebuilt one.

| Shape (K × N) | Weights | `mul_mat_vec_q` | `mmvq_k80_q4_K` | Speedup |
|---|--:|--:|--:|--:|
| 4096 × 4096 | 9.4 MB | 196–219 µs | 136–137 µs | 1.4–1.6× |
| 4096 × 14336 | 33.0 MB | 584–668 µs | 341–419 µs | 1.4–2.0× |
| 14336 × 4096 | 33.0 MB | 543–625 µs | 302–341 µs | 1.6–2.1× |

- **Ceiling.** A plain read of the same 33 MB reaches 148–157 GB/s, not the 240 GB/s spec (ECC
  and clocks). On the 33 MB shapes ggml's kernel reads 49–61 GB/s, about a third of that; the
  FP32 kernel reads 79–109 GB/s, about 50–70 %.
- **Accuracy.** Against a double-precision dot of ggml's own CPU dequantization, the FP32 kernel's
  max relative error is 2.4e-7; `mul_mat_vec_q` is 5.5e-3, from rounding the input to `q8_1`.
- **Prep.** Both paths launch a ~5 µs kernel on the input first (`quantize_q8_1` or
  `mmvq_k80_prep`).
- **Launch shape.** 4 rows per warp and 4 warps per block. With 1 row per warp the kernel is no
  faster than ggml's; 2, 4 and 8 sit within run-to-run noise of each other.

## Limits of this measurement

- **No hardware counters.** `nvprof --metrics` needs profiling permission on this host
  (`ERR_NVGPUCTRPERM`), so where the remaining 40 % goes is unmeasured.
- **No per-kernel profile of a real decode.** `nvprof` around the ollama runner, and metric replay
  around ggml, fail with `unknown error`. The end-to-end rows above stand in for it.
- **Clocks drift.** Under load the die sits at its power cap and auto boost moves the SM clock
  between 562 and 666 MHz, so single kernel timings vary by up to 20 %.
