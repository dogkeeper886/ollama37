# q6_K mat-vec with FP32 decode on the K80 (#567)

| | |
|---|---|
| Build | branch `study-567-k80-q6k` on `5bcc8c75` (#563 and #565 merged), version 2.3.3-567 |
| Baseline | CI run 37773830995 (`main`'s kernels), same host |
| Host | 4 × Tesla K80 dies (sm_37), CUDA 11.4, driver 470.256.02; lab runs on die 1 |
| Measured | 2026-10-08 to 2026-10-09 |

Q4_K_M models keep `attn_v`, part of `ffn_down` and usually the output head in q6_K. After #563
moved q4_K to an FP32-decode kernel, q6_K still ran on ggml's `mul_mat_vec_q` at ~75 GB/s and took
~27 % of a `llama3.1:8b` decode token. `mmvq_k80_q6_K` rebuilds each 6-bit value from `ql` and `qh`
with masks, so its bytes keep the bit positions #563's input prep scales by, and decodes them to
FP32 with an OR and an FADD. Each byte's decode constant also subtracts the "- 32", exactly. It
sits beside #563's kernel in `mmvq-k80.cu` and behind the same Kepler-only, batch-1 gate.

## Correctness

Both checks hold the model fixed:

- **Against an exact reference:** max relative error 1.1–1.4e-7 against a double-precision
  computation over ggml's own CPU dequantization; `mul_mat_vec_q` is 4.7–6.4e-3, from rounding the
  input to `q8_1`.
- **Against the old build:** 20 of 25 replies are word for word identical to run 37773830995. The
  other 5 say the same in other words ("let me try to tackle" against "let me tackle", "one exact
  word" against "one word"; `deepseek-r1:1.5b` now quotes Lincoln's "colored slaves").

## Kernel, one die

Lab runs at the q6_K shapes against `mul_mat_vec_q`, `nvprof` kernel times. Kernel times drift up
to 25 % between runs with the die's clock, so only ratios within one run are compared.

| Shape (K × N) | Like | Speedup, first version | With the "- 32" folded |
|---|---|--:|--:|
| 4096 × 1024 | `attn_v` | 1.08× | +4 % on top |
| 14336 × 4096 | `ffn_down` | 1.20× | +10 % on top |
| 4096 × 32768 | output head | 1.20× | +2 % on top |

- **q6_K is arithmetic-bound on Kepler,** unlike q4_K. Rebuilding and multiplying a 6-bit value takes
  ~7 instructions, against ~4–5 for q4_K, so the kernel reads ~94 G values/s against q4_K's ~156 G on
  the same die, below the die's memory speed.
- **What did not help:** coalesced 32-bit loads staged through shared memory (a pair of 210-byte
  blocks is 4-byte aligned), sharing the input vector across a thread block's warps, and 4 or 8 rows
  per warp. 2 rows per warp keeps registers low and is fastest.
- **Code review (`/code-review`)** found no correctness bug and three cleanups, all applied: the
  "- 32" folded into the decode constants (no per-block input sums), `ysum16` computed only for q4_K,
  and the 16-byte alignment check kept to q4_K. Wider scale loads were not taken: the scale bytes can
  start at an odd address.

## Limits

- **One run per row** in CI.
- **Not covered:** MoE expert layers (`mul_mat_id`) and batch 2–8 keep ggml's path.
- **A larger q6_K gain would need repacking at load time** into an aligned layout with ready scales;
  that changes the weight layout and is a separate change.
