# K80 q4_K/q6_K mat-vec: one PRMT per value (#584)

| | |
|---|---|
| Build | branch `study-584-k80-mmvq-prmt` on `43a5d606`, version 2.3.3-584 |
| Baseline | CI run 37976473036 (`main`'s kernels), same host |
| Host | 4 × Tesla K80 dies (sm_37), CUDA 11.4, driver 470.256.02; lab runs on die 1 |
| Measured | 2026-10-10 to 2026-10-11 |

Every CI model decodes through the K80 FP32 mat-vec kernels (#563 q4_K, #567 q6_K, #572 their expert
form). They decoded each value with a mask and an OR into the mantissa of 2^23, a subtract and an FMA.
One PRMT (`__byte_perm`) now builds the same float from the value's byte and the 0x4B exponent byte,
replacing the mask and the OR. Every value lands at byte 0, so `mmvq_k80_prep` no longer scales its
inputs by position. The arithmetic is unchanged and the results are bit-identical.

## What limits the kernels

`cuobjdump -sass`, `ptxas -v`:

| Kernel | Registers | SASS instructions | Main kinds |
|---|--:|--:|---|
| `mmvq_k80_q4_K` | 92 | 927 | LOP32I 237, FADD 168, FFMA 140, IMAD 55, SHR 54, BFE 33 |
| `mmvq_k80_q6_K` | 63 | 467 | LOP32I 86, IADD 58, FADD 42, FFMA 34 |

- **Instructions per byte:** the q4_K decode core was 4 instructions per value (AND, OR, FADD, FFMA),
  about 6 per value with scales, addresses and the loop. Reading 150 GB/s would need about 4
  warp-instructions per clock per SM, which is near what Kepler issues. So the kernels are bound by
  instructions per byte, not by memory.
- **No profiler counters:** the hardware counters need root (`ERR_NVGPUCTRPERM`), so this rests on the
  SASS and on timed variants.

Lab, one die, `ggml_mul_mat` at batch 1 against a plain read of the same bytes. Busy means back to back.
Part-idle means 15 ms on and 30 ms off, as a die of a 3-die model decodes, and the die then runs at its
562 MHz base clock:

| Kernel | Busy GB/s (% of plain read) | SM clock while busy | Part-idle GB/s (% of plain read) |
|---|---|--:|---|
| q4_K 4096×14336 | 96.0 (61 %) | 705 MHz | 76.7 (59 %) |
| q4_K 14336×4096 | 96.3 (61 %) | 730 MHz | 74.9 (57 %) |
| q4_K 4096×4096 | 85.2 (58 %) | 797 MHz | 62.5 (52 %) |
| q6_K 14336×4096 | 77.4 (49 %) | 653 MHz | 66.6 (51 %) |
| q6_K 4096×4096 | 74.9 (49 %) | 705 MHz | 60.7 (49 %) |
| plain read | 147–159 GB/s | 875 MHz | 120–131 GB/s |

- **Read efficiency:** the kernels read 49–61 % of a plain read at both duties.
- **Clock:** run back to back they hold the SM clock at 653–797 MHz, where a plain read holds 875.
- **What follows:** fewer instructions per byte also means less power, and so a higher clock.

## Variants, standalone q4_K kernel

Alternating rounds, part-idle duty (562 MHz):

| Shape | Now | V1: PRMT | V2: PRMT, no subtract |
|---|--:|--:|--:|
| q4_K 4096×14336 | 410.4 µs | 367.7 (−10.4 %) | 346.6 (−15.5 %) |
| q4_K 14336×4096 | 423.6 µs | 381.6 (−9.9 %) | 366.6 (−13.5 %) |
| q4_K 4096×4096 | 134.5 µs | 121.4 (−9.7 %) | 114.9 (−14.6 %) |
| max relative error | 1.9–3.1e-7 | identical | 2.6–3.9e-6 |

- **V2** builds 0x43vv0000 = 128 + v and takes 128 × the 16-value input sum out once per group. That
  removes the subtract, but it cancels a large term, so the error rises 13–19×.
- **Kept: V1,** because it is bit-identical.
- **Busy runs** give the same order.

## Decision

**Keep.** Decode rises on every model that uses q4_K or q6_K weights, and the replies don't change.

## Limits

- **One CI run per row.**
- **The kernels still read about 60–70 % of a plain read:** V2's extra 5 % was left out to keep results
  bit-identical. Other overhead, such as scale decode, addressing and the loop, is still about a third of
  the instructions.
